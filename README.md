# Triage Desk

AI-assisted triage of player bug reports into prioritized, Jira-ready tickets, with duplicate detection, an explicit severity rubric and human review. Evaluated against labeled data.

> All data in this repo is synthetic. "Neon Drift" is a fictional game, and every message, username and order ID was generated by `generate_data.py`.

## The problem

A live mobile game's Discord gets hundreds of messages a day. Most of them are not bugs: feature requests, complaints about prices, questions, spam. The bug reports that are there come in duplicates written ten different ways, half in Turkish, mostly without device, OS or game version. QA has to find the three that matter (the payment bug, the launch crash, the lost cars) before the end of the day, and turn them into tickets a developer can act on.

Triage Desk does the first pass and leaves the decisions to a person:

```
146 Discord messages
  └─ 1 classify      bug / feature request / feedback / question / spam
  └─ 2 extract       platform, OS, device, game version, frequency, money impact
  └─ 3 group         duplicates → issues (confidence score, representative report)
  └─ 4 severity      rubric (S1–S4) + priority (P1–P4), reasoning per issue
  └─ 5 tickets       Jira-ready draft: environment, steps (inferred ones marked), expected/actual, missing info
  └─ 6 replies       friendly EN/TR replies asking players for device / OS / version / screenshot
  └─ 7 export        Jira CSV · daily triage summary (markdown) · JSON
        └─ review.html   human approves, edits, merges, splits, re-rates → exports approved tickets only
```

**The tool never files anything on its own.** Everything it writes is a draft until someone approves it in the review UI. Player replies are drafts you copy into Discord yourself.

## Two modes

| | AI mode (`ANTHROPIC_API_KEY` set) | Rule-based mode (no key) |
|---|---|---|
| Classify + extract | `claude-haiku-5-5`, batched, structured outputs | EN/TR keyword lists, regex for devices/OS/versions |
| Group duplicates | `claude-sonnet-5-5` sees all bug reports at once | TF-IDF (word + char n-grams) + EN/TR synonym concepts, agglomerative clustering |
| Severity | Sonnet picks the impact category and explains it; **the rubric code applies the levels** | keyword category vote; same rubric code |
| Tickets | Sonnet drafts each ticket | templates per category, all steps marked inferred |

All Claude calls go through `llm.py`, which uses the official `anthropic` SDK's `messages.parse()` with Pydantic models, so every response is validated against a schema. The wrapper raises on refusals or truncated output. Sonnet calls enable the server-side refusal fallback. Responses are cached on disk (`out/.llm_cache/`), so re-runs don't cost anything. If the model drops or invents a message ID, the pipeline repairs it: unknown IDs are dropped, and forgotten reports become their own issue, so a report never silently disappears.

## Severity rubric

This is the part an interviewer will push on, so it's explicit, written down, and lives in one file ([severity.py](severity.py)).

| Severity | Impact category | Examples in Neon Drift |
|---|---|---|
| **S1** | Crash, data loss, or real money lost | launch crash, cars missing after update, coins charged but not delivered, VIP not restored |
| **S2** | Major feature broken or progression blocked | tutorial soft-lock, race freeze, multiplayer disconnect, leaderboard not updating |
| **S3** | Feature degraded, workaround exists | audio gone after an ad (restart fixes it), daily reward timer reset |
| **S4** | Cosmetic | Turkish text overflowing a button, paint flicker |

**Escalations**
- **E1, money:** if at least a third of the reports involve real money, the issue is S1. Charging players without delivering the item damages trust, creates refund and store-policy risk, and costs revenue.
- **E2, volume:** 10 or more reports raise severity by one level, but **volume alone never makes something S1**. A loud cosmetic bug is still not a crash.

**Priority** (how soon to work on it) starts at the severity level and then:
- 5 or more reports → one level more urgent (it's widespread)
- a single report of an S3/S4 issue → one level less urgent until someone confirms it
- money involved → always P1

Why does AI mode only pick the *category*? Severity has to be consistent and defensible. Letting a model choose "S2" directly makes it drift with wording and with how angry players sound. The model judges what kind of defect this is, which is the hard language problem. The levels come from fixed rules a QA lead can audit and change in one place. Every issue shows its reasoning chain in the UI and in the Jira description, e.g. *"Category: payment → base S1. P-c: money involved → P1."*

## Evaluation

`python triage.py evaluate` runs the pipeline and compares it with `data/ground_truth.json`: 146 messages, 12 planted bugs with 3–14 reports each, and 8 vague "game broken pls fix" reports.

| Metric | rules | AI |
|---|---|---|
| Classification accuracy (146 msgs) | 95.9% | *not run yet* |
| Planted bug reports classified as bug | 97.7% | |
| Issues produced (12 planted bugs) | 13 | |
| Planted bugs found as one clean issue¹ | 12/12 | |
| Duplicate pairs precision / recall | 0.97 / 0.85 | |
| Duplicate pairs F1 | 0.91 | |
| Severity exact match | 12/12 | |
| Severity within one level | 12/12 | |
| S1 bugs missed | 0/4 | |

¹ One issue holds at least 80% of that bug's reports, and at least 80% of that issue's reports belong to that bug.

**Read these numbers honestly.** The rule-based keyword lists, synonym concepts and clustering threshold (0.85, picked from a 0.6–0.9 sweep) were written while looking at this same synthetic dataset. Rule mode is effectively tuned on its test set, so treat its numbers as an upper bound, not a forecast. The interesting comparison is AI mode, which has seen none of this. To fill in the AI column:

```powershell
$env:ANTHROPIC_API_KEY = "sk-ant-..."
python triage.py evaluate
```

A full AI run is about 35 API calls: 11 small Haiku batches (classify + extract), 1 Sonnet grouping call, then 1 severity call and 1 ticket call per issue. That costs well under a dollar, and cached re-runs cost nothing.

The per-bug breakdown (which issue each planted bug landed in, and whether it was split) is written to `out/eval_report.md`.

## Review UI

`python triage.py run` writes `out/review.html` with the run's data embedded. Open it straight from disk. It's a single file with no build step and no server.

_Screenshot / GIF coming soon (approve an issue, merge one, split a report out, export)._

- Issue list sorted by priority, with report count, severity badge, money flag and grouping-confidence bar
- Issue detail: drafted ticket, severity reasoning, all linked player messages (representative marked)
- **Approve**, **edit** the ticket, **change severity / priority**, **merge** two issues (keeps the higher severity), **split** a wrongly grouped report into its own issue
- **Export approved CSV**: same Jira columns as `jira_import.csv`, approved tickets only
- Player-replies tab with copy buttons; replies are drafts only
- Light/dark theme, works at phone width; review decisions are saved in the browser per run

## How to run

```powershell
pip install -r requirements.txt
python triage.py generate          # optional: recreate data/ (deterministic, seed 42)
python triage.py run               # AI mode if ANTHROPIC_API_KEY is set, else rule-based
python triage.py run --mode rules  # force rule-based
python triage.py evaluate          # metrics vs ground truth (rules, plus AI when a key is set)
python -m pytest                   # 26 tests, Anthropic API mocked
```

Outputs in `out/`: `triage.json`, `jira_import.csv`, `daily_summary.md`, `review.html`, `eval_report.md`.

## Limitations

- **Synthetic data.** 146 messages written for this project. Real Discord traffic is messier: memes, threads, replies quoting other players, sarcasm, other languages, and screenshots that actually contain the information. The tool needs real (anonymized) reports to tune and evaluate against.
- **Rule mode is overfit** to this dataset (see Evaluation). With new bug types its keyword lists will miss things.
- **Grouping is per run.** There is no memory of yesterday's issues and no matching against existing Jira tickets, which a real deployment would need ("this is ND-042 again, +6 reports").
- **Steps to reproduce are mostly inferred.** Players rarely give steps, so most steps are marked *inferred, needs verification*. That marking is deliberate, not a gap to hide.
- **Replies are templates**, not AI-written. That keeps the tone and promises consistent; a community manager may want to adjust them.
- **Severity from text only.** Real triage would also use crash analytics, store refund data and how many players are affected, not just how many wrote in.
